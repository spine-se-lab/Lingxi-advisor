# Lingxi Advisor 分析与优化建议

核查日期：2026-09-16（America/Toronto）。代码基线：`ab147706bdd5505a77eaf420c9d8e5795aca43e1`；插件 `0.2.0`，LingxiAdvisor `0.7.0`。
主任务：[#3](https://github.com/yiikou/CodeHelix-Plugin/issues/3)。本文记录本轮代码审计、隔离复现和建议，未实施插件改造，也未更新 GitHub Issue。

## 目标与判断

优化后，用户应能在 Chrys / OpenCode 中按实际模型能力完成任务模式检索、应用和知识准备；关闭知识更新时，Agent 的指令与服务端权限一致；安装、重启、升级和移除都不依赖原开发目录，也不把凭据保存到文件。

Issue #3 的统一安装方向成立。按用户确认的顺序，第一阶段先完成新安装流程，将入口、JSONC、依赖锁、Secret 和能力前置检查等必要修复纳入迁移；第二阶段再整理插件内部实现和业务行为。保留已锁定的上游业务实现，检索性能和缓存策略单独测量，不能把安装迁移等同于效果优化。

本文中的工作均是建议实施范围；Issue 现有验收要求仍有效。新增发现按事项并入同一个 #3，不另拆本插件的 Bug 单。

## 已有基础与系统职责

- 两个 MCP 已经共用同一 Python 环境：同一个 `lingxi-advisor-mcp`，分别使用 `runtime` / `operator` profile。迁移目标是统一管理现有环境，不是先合并两个 venv。
- Source 已有共同 installer，以及 Chrys、OpenCode 两个 Adapter；没有 Chrys 源码 Patch。无需为了目录形式重写业务包。
- 上游来源不仅是 commit：应保留 `import-lock.json` 中的 revision、已审计 overlay 和 archive digest。不能把这个 release 说成无额外变更的纯上游 HEAD。
- 当前两个 Target 都未声明 `managed_install`。`RuntimeLayout` 把 release、venv、Secret 文件、数据、export 和私有状态放在目标配置根下；installer 未消费 `request.managed`。
- 共享框架已经提供 PackageStore、Python Runtime、配置引用、Skill 投影、状态和事务。迁移指南中“共享 core 正在实施”的叙述需要按当前提交修订；框架可用不代表本插件已接入。

### 当前构成与建议改造后的构成

当前插件是上游业务制品加 CodeHelix 接入代码。业务的两条使用路径是：Runtime 在编码任务中检索历史知识并通过 Apply 返回可用内容；Operator 执行知识准备、批任务与结果读取。Apply 的“应用”是组织和校验知识内容，不是替 Agent 修改代码。

| 部分 | 当前构成 | 建议改成什么样 |
|---|---|---|
| 业务核心 | 上游 zip 中的一个 lingxi-advisor wheel，包含检索、时间/安全检查、LLM Gate、Light/Grounded Generation、Artifact Store 和 batch | 保留一个版本化上游核心；业务语义/性能修复在上游完成，通过导入锁更新 |
| Agent 工作指令 | 两个上游 Skill，安装时再拼接 CodeHelix defaults | 两个构建期固定的 canonical Skill；指令遵循实际能力及用户配置，安装仅投影 |
| 对外工具 | 同一个 lingxi-advisor-mcp 程序的 runtime / operator 两个 profile，分别 2 / 6 个工具 | 保留两个工具面和一个 Runtime；统一经 launcher 启动，保留 profile 区别 |
| 共同安装实现 | installer.py 同时做部署参数、Secret 文件、私有 release/venv、Skill 改写、接线、私有状态与 verify | 收窄为四阶段协议及插件专属校验；使用 managed refs，通用安装生命周期交给 Kit |
| 运行期启动 | 两宿主直接运行私有 venv 内命令，读取 runtime.env | 一个薄 launcher 读取非敏感部署配置、验证/映射启动环境、关闭 dotenv 兜底并启动指定 profile |
| 宿主适配 | Chrys Profile 与 OpenCode JSONC/Skill/MCP，夹有路径和运行环境假设 | Adapter 接收准备好的启动命令及 Skill 引用，只处理宿主格式、注册所有权、能力及加载验证 |
| 构建与交付 | 一个 Source 生成两个自包含 Delivery，含上游包、installer、contracts、locks | 保留来源形态；修执行权限/确定性，增加完整 MCP 依赖锁和 managed 声明 |

建议的安装落点如下。PackageStore 是运行制品，Runtime 是解释器/依赖，Activation 是 Agent 配置接线；三者职责不同。

| 安装对象 | 建议落点/方式 |
|---|---|
| 固定 wheel、Skill、launcher、Adapter、contracts | `~/.codehelix/package-store/` 内完整 Delivery |
| 一个 Python 环境，供两个 MCP 使用 | `~/.codehelix/runtimes/` |
| model、endpoint、data root、更新开关等非敏感配置 | `~/.codehelix/config/` |
| 安装事实、引用及所有权 | 共享 State |
| Skill 与 MCP / Chrys Profile | Agent 自己的目录和配置，通过 Activation 引用固定制品 |
| 知识、batch、outputs | 保留原数据目录或显式选择新目录，用 DataRef 记录；移除不删除 |
| token/key | Agent 启动环境，launcher 仅在进程中映射 |

目录调整应服务这些职责：继续保留 `source/upstream/`、`source/installer/adapters/`、`targets/`、`contracts/`、`build-delivery`；新增小的运行期 launcher 和依赖锁即可开始。`release.py` 的 release 校验继续供构建使用，`exports.py` 继续负责公开绑定；`layout.py` 改为使用 managed 引用而非创建私有布局。`ownership.py` 中重复的安装状态职责交回框架，宿主字段归属检查保留在 Adapter。是否进一步拆分 installer 文件，以最终职责和测试需要决定，不先建立通用插件框架或第二份 LingxiAdvisor 包。

## 优先解决的具体问题

### 1. OpenCode 配置编辑会损坏合法 JSONC

**已离线复现。** 输入 `{"theme":"dark",}` 后，`render_config()` 生成以 `{"theme":"dark",,` 开头的内容。已有 `mcp` 对象带尾逗号时也受影响。`_set_property()` 在新增属性时无条件补逗号，`install_binding()` 没有先校验生成结果就写入文件。

另外，`_strip_jsonc()` 最后的全局正则会把字符串值 `https://example.test/,}` 解析成 `https://example.test/}`。这项会影响解析和比较；本轮没有观察到它直接改写原字符串的落盘字节。

证据：`source/installer/adapters/opencode.py:129`、`:142`、`:231`、`:275`。

建议由 Adapter 使用仓库已有 `jsonc-parser` 能力做语法感知的字段修改，或提供等价且经过测试的实现。必须保留注释、未知字段和其他 MCP，只修改本插件的两个注册；写入前重新解析。验收覆盖根对象/嵌套对象的尾逗号、字符串内逗号与括号、注释、重复安装和发生冲突时不写入。

### 2. 关闭知识更新后，Skill 仍要求更新

**已确认指令与代码冲突。** `_desired_files()` 总是追加固定说明，要求 runtime 首次 search 和 operator preparation 传 `update_preretrieved=true`；设置 `allow_preretrieved_updates=false` 时，启动命令却不授权这个动作，上游会拒绝相应请求。

证据：`source/installer/installer.py:205`、`:218`、`:248`；`source/installer/layout.py:74`；wheel 内 `lingxi-advisor/adapters/mcp/runtime_tools.py:205`。

应把固定说明移到 build 形成 canonical Skill，并改成遵循当前服务能力：仅在服务器允许且本次任务需要时请求持久化更新。关闭更新与“不生成知识”是不同开关，不应混为只读模式。验收要实际调用关闭更新后的合法 search/preparation，不能只检查启动参数。

### 3. Runtime sampling 不等于 Operator 可生成知识

**已通过 wheel 代码与离线能力查询确认。** Runtime 分支创建 Host sampling bridge；Operator 分支没有这项接入，生成知识需要 generator key/model。当前免模型安装说明容易让人以为两个 profile 都能借用 Agent 模型。

无独立 Judge/Generator 配置的离线查询仍返回 `generation_modes=[light, grounded_analysis]` 和 `allow_live_search=true`；它们描述支持的模式/策略，不证明模型已就绪。batch 另有自己的 configured 状态。

建议对用户明确展示以下能力，而不只给一个“安装成功”：

| 功能 | 必须核实的条件 | 条件不足时的行为 |
|---|---|---|
| Runtime 读取已有知识 | 数据可读、对应知识存在 | 明确返回命中/未命中；不承诺能补齐知识 |
| Runtime 首次 Gate / Generation | 可用独立模型，或实际支持 sampling 的宿主 | 在触发长任务前解释缺失能力 |
| Operator 生成知识 | 当前 release 所需的独立模型配置 | 报出缺失配置项，不能用 Runtime sampling 的成功替代 |
| Operator batch | 模型、batch 输入/存储等实际条件满足 | 明确指出未配置的能力，并以受控 batch 完成验收 |

证据：wheel 内 `lingxi-advisor/adapters/mcp/server.py:95`、`:140`，`lingxi-advisor/api.py:237`。本轮未实测当前安装的 Chrys/OpenCode sampling 支持程度，不把旧版 OpenCode 的限制推广到全部版本。

保留 0.7.0 时可以先准确诊断并要求独立模型；为 Operator 新增 sampling 属于上游能力工作，不应暗中加入本次安装迁移。

### 4. 凭据迁移必须同时切断 dotenv 兜底

**当前确实持久化凭据。** `_env_bytes()` 将 GitHub token 和 Judge/Generator key 写入 `runtime.env`，再由 MCP 的 `--env-file` 读取。`0600` 权限不满足仓库现有的“Secret 不落盘”合同。

**已离线复现另一个迁移陷阱：** 仅删除 `--env-file` 参数仍会调用 `_load_dotenv(<project_root>/.env)`；在启动环境缺值时，旧文件仍能补入凭据。证据为 wheel 内 `lingxi-advisor/adapters/mcp/server.py:177`、`:252`。

推荐先明确无 dotenv 的启动方式：上游增加显式禁用选项，或本仓薄 launcher 调用 `create_mcp_server(...).run()` 绕开 CLI 的 dotenv 加载。launcher 只承担配置与环境映射，不复制检索业务。缺 Secret 的验收应在数据根放置带测试标记的旧 `.env`，确认它不会使启动或模型调用意外恢复。

迁移还必须完整声明 `GITHUB_TOKEN_1…15`。当前 Kit 的 `declaredEnvironment()` 不展开 `repeatable`；用当前 manifest 和测试变量运行 `runtimeEnvironment()`，编号 token 会被过滤。**这是仅添加 managed 声明会引入的问题，不是已经证实当前 legacy CLI 丢 token。** 建议显式补全允许传递的变量，保留共享模型 key 到 Judge/Generator 的运行期映射。

证据：`source/installer/installer.py:178`；`plugin-kit/process/environment.js:14`；`plugin-kit/installation/orchestrator.js:101`。适用合同见 [custom 协议](../../../docs/specifications/custom-installer-protocol.md)。

### 5. 入口权限与重建需要分别修复

**权限故障已复现。** Git 记录的插件入口、两个 Delivery bin 和 `build-delivery` 均为 `100644`。冷 npm cache 会把 bin 改成可执行，掩盖问题；热 cache 再遇到恢复为提交权限的文件，两个目标都返回 exit 126，协议根本未启动。保留 `0644` 的隔离副本执行根 CLI build，也返回 EACCES。

现有 clean rebuild 测试先给副本 `build-delivery` 做 `chmod(0755)`，因此无法证明新检出的构建入口可用。应修正应提交的 executable mode / 调用方式，并覆盖未预处理的新检出及冷、热 npm cache；不能把测试里补权限当作修复。

**重建漂移已定位。** 两个目标都只变化 `CHECKSUMS.sha256`、`source-lock.json`、`delivery-lock.json`。校验清单条目顺序变化，连带改变 release 摘要；业务 payload 字节相同，同环境连续两次隔离构建也相同。这是提交制品与当前生成结果不一致，不能称为随机构建不稳定或业务代码漂移。

建议将排序键显式固定为相对 POSIX 路径字符串，再从 Source 重建、审阅、同步两个目标的 Delivery。`sorted(Path)` 的跨平台语义差异是待核实成因，本轮没有执行历史 Kit / Windows 对照，不能断言历史责任。

证据：`build-delivery:31`、`:81`；`tests/test_delivery_locks.py:130`；`plugin-kit/cli/contributor-cli.js:175`。

## 统一安装迁移中应落到实处的事项

1. **一个受管 Runtime，并冻结 `[mcp]` 依赖。** 当前 installer 安装 `wheel[mcp]`，但依赖未冻结。现有共享 Runtime 支持 `requirements`、`--require-hashes` 和随后 `--no-deps` 安装主制品，可生成包含 MCP extra 传递依赖的锁并验证。不应只声明裸 wheel，依赖它自动提供完整 MCP 环境。参见 `plugin-kit/installation/runtime.js:192`。
2. **解释器声明与入口一致。** Target 写 `python>=3.10`，installer 却无条件导入需要 Python 3.11 的 `tomllib`；两个目标均导入 Chrys Adapter。protocol shim 选择第一个存在的 Python，不做版本筛选。此为静态确认，未用 Python 3.10 实跑；应选定并验证实际 installer/runtime 解释器，避免只修改文字要求。
3. **DataRef 对应真实路径。** 两个 Target 都缺中英文知识名称/说明；补齐标签，并使可配置数据根、MCP `project-root` 与 DataRef 指向同一位置。知识资产、batch 状态、可重建缓存和临时输出应说明用途，升级/移除保留现有业务数据。仅写入 DataRef 不代表数据已可读或被运行时使用。参见 [数据规范](../../../docs/specifications/plugin-data.md)。
4. **复用现有所有权保护，再补宿主级验证。** 当前已有 hash/内容比较，会拒绝不同内容的同名注册和未知 Skill 文件；不能把它描述为任意覆盖用户配置。OpenCode verify 对 `mcp list` 只检查退出码和名称，模拟“名称存在但 failed”的输出会被接受；这说明判定不足，尚未证明真实 OpenCode 的失败输出格式。独立 MCP initialize/tools-list 探针已存在，仍需补宿主真正连接的证据。
5. **Chrys 检查聚焦所需能力。** 版本门禁、Profile schema 和全仓 tracked 状态摘要混在验收中。保留必要 loader/schema/注册探针，收窄无关源码变化造成的干扰。不能仅凭新版本号宣称兼容，仍遵循协议的已验证、通过但未验证、缺能力三种结果。
6. **保持 runtime export 的可调用合同。** v1 的 command 数组可以指向固定 launcher，未必需要改 schema；operator 不能直接塞入 v1，它明确限制一个 runtime Skill/Server。README 称组合插件“继续消费”export，但本仓搜索未发现组合 installer 读取它，组合包仍自带 runtime。应先列明已知消费者和 contract fixture；将真实组合迁移留在其自己的范围，不虚构已有集成验证。

具体三安装场景仍按 #3：完整仓库 CLI、独立 Delivery CLI、CodeHelix Plugin Management。不能以一条直接执行 MCP 的测试替代三入口或两宿主验收。现有 [测试规范](../../../docs/contributing/testing-and-acceptance.md) 与 [贡献流程](../../../docs/contributing/contributing-plugin.md) 是交付依据。

## 上游行为优化：先澄清语义，再测成本

发现一个值得后续核实的调用语义问题：Skill 把 `prepare_if_missing=false` 称为后续“cache-only”查询，但它主要阻止知识生成。离线分支选择验证中，带 `repo+issue_number` 或完整 `repo+instance_id+base_commit` 的请求仍选择 live-instance 路径；代码在预检索未命中后可以继续 live 检索和 Gate。因此它不是严格的“不联网、不调用模型”开关。证据为 wheel 内 `lingxi-advisor/capabilities/activate/lingxi-advisor_search/contracts.py:130`、`lingxi-advisor/internal/search_retrieval/service.py:313`，以及 release Skill 的 search 调用说明。

本期可先修正 Skill 的承诺；如果产品确实需要严格 cache-only，再由上游定义清楚的读取模式，并验证完整任务上下文下也不触发 GitHub/LLM。不要仅凭一次分支检查断言真实调用次数或延迟。

性能优化应记录冷启动、首次检索、知识命中、重复 apply、batch 的耗时、GitHub 请求数、模型调用数和缓存命中数，再决定是否优化检索路由或复用。**本轮未跑线上任务，没有证据支持给出性能收益百分比。**
